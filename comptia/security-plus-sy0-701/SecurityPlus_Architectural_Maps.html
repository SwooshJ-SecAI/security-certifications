1 · Zero Trust — Per-Request Evaluation

1.2Application → Analysis

Zero trust removes location as a trust signal. Every request is re-evaluated by the control plane (decision) and enforced by the data plane (action) — separating "who decides" from "who enforces" so policy scales independently of where the resource lives.

Subject + Device
User/service makes a request; carries identity & device posture
REQUEST→
Policy Engine
Control plane — scores identity, device health, context, risk
VERDICT→
Policy Administrator
Control plane — issues/revokes the session credential
↓
Meets policy right now?
Allow → Data Plane enforces
Policy Enforcement Point
Grants a scoped, time-bound session to the specific resource — nothing more
Deny / revoke
Session dropped
Failed device-posture or risk check ends access mid-session — no lateral free pass
Why it works

The perimeter model trusted anything "inside," so one breach enabled free lateral movement. Re-verifying every request against live context means a stolen credential alone is insufficient — the device and risk signals must also pass, every time.

Fails when

The policy engine trusts a stale signal (cached posture, long-lived token) or the enforcement point is bypassable via a flat network path — reintroducing the implicit trust zero trust was meant to remove.

2 · Incident Response Lifecycle — Why Order Is Causal

4.8Application → Analysis

The seven phases run in sequence because each creates the precondition the next depends on. The gates (amber) are the exam's favorite traps — skip one and the later phase fails.

1
Preparation
Plans, tooling, comms trees, and training staged before any incident.
2
Detection
Alert/indicator surfaces a possible incident (SIEM, EDR, user report).
3
Analysis
Confirm it's real and scope it — which hosts, accounts, data.
GATE → must know scope before you can contain the right things
4
Containment
Isolate hosts, disable accounts to stop the spread.
GATE → must cut the attacker's channel before removing malware
5
Eradication
Remove malware, backdoors, and the vulnerable config.
6
Recovery
Restore validated systems from clean backups; monitor closely.
7
Lessons Learned
Root-cause review feeds improvements back into Preparation (the loop closes).
Fails when

Eradication runs before containment → attacker re-enters through the still-open channel. Or systems are wiped before forensic capture → evidence and chain of custody are destroyed, so root cause is never found.

3 · Firewall Rule Ordering — First-Match Logic

4.5Analysis · PBQ

Firewalls evaluate top-down and act on the first matching rule, then stop. Order encodes logic: a broad rule above a specific one shadows it. Trace the flow "permit HTTPS to WebServer; block all else to its subnet" against two orderings:

Correct order — specific first
1permit tcp any → Web 443MATCH ✓
2deny ip any → WebSubnetreached only if no match above
3implicit deny-alldefault
Result
HTTPS to the web server is permitted; everything else to the subnet is denied. Intended policy holds.
Wrong order — broad first
1deny ip any → WebSubnetMATCH ✗
2permit tcp any → Web 443never evaluated
3implicit deny-alldefault
Result
The broad deny matches first and stops evaluation — the permit never fires. Legitimate HTTPS is blocked.
Why it works

Because evaluation halts at the first match, specificity must decrease as you go down. The implicit deny-all at the bottom is a fail-safe default: anything not explicitly permitted is dropped.

Fails when

An "allow any" rule drifts to the top during a change — it matches everything and silently nullifies every rule below it.

4 · Quantitative Risk — Is the Control Worth It?

5.2Application → Analysis

Risk math converts exposure into dollars so a control decision becomes a calculation, not an opinion. The chain builds ALE, then compares it to the control's annual cost.

Asset Value × Exposure Factor

=→
SLE = $30,000
Single Loss Expectancy — one event
× ARO→
ALE = $6,000/yr
SLE $30k × ARO 0.2 (once / 5 yrs)
↓
Control's annual cost < $6,000 ALE?
Yes → justified
$2,000/yr flood control
Removes $6k risk for $2k → net saving. Economically sound (mitigate).
No → not justified
$9,000/yr control
Costs more than the risk it removes → accept the risk or find a cheaper option.
Why it works

ALE is the common currency that lets you compare unlike risks and controls objectively. A control is worth buying only when it reduces ALE by more than it costs — the core cost/benefit test behind treatment choices (mitigate / transfer / accept / avoid).

5 · Defense in Depth — Mapping Controls to a Ransomware Kill Chain

2.5 · 2.4Application → Analysis

No single control is complete, so layers are chosen so a failure of one is contained by the next. Each attack stage (blue) maps to the control (green) that limits it.

A
Initial access — phishing link clicked
Control: awareness training + email security (SPF/DKIM/DMARC) lowers the click rate and blocks spoofed senders.
B
Execution + privilege escalation
Control: least privilege limits what the account can reach; EDR detects the malicious process behavior.
C
Lateral movement across the network
Control: network segmentation contains the blast radius to one VLAN — the malware can't reach other zones.
D
Encryption of files (impact)
Control: offline/immutable backups (corrective) enable recovery without paying; monitoring flags the mass-write spike.
Why it works

The layers are independent in kind — prevention, detection, containment, recovery — so defeating one does not defeat the rest. Diversity across control types matters more than the raw number of controls.

Fails when

Layers are redundant in kind (e.g. three detective tools, no containment or recovery). The attacker is seen at every step but never stopped, and there's no clean restore point.
